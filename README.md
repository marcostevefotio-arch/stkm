# REDAMS-STK SaaS v2

Prototype SaaS multi-tenant pour centre de santé et pharmacie. Choix retenus : MySQL partagé, abonnement mensuel, branding personnalisé par établissement, sans Docker.

## Installation Windows 11
Prérequis : Node.js 20+, MySQL 8, VS Code.
```powershell
npm install
Copy-Item .env.example .env
```
Crée ensuite la base :
```sql
CREATE DATABASE redams_stk_v2 CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```
Configure `.env`, puis :
```powershell
npm run db:init
npm run db:seed
npm run dev
```
Ouvre http://localhost:3000

Compte de démonstration de l’établissement : `admin@demo.redams-stk.local` (mot de passe de démonstration disponible dans votre configuration de développement).

## Accéder à l’espace de gestion des organisations et abonnements (Super Admin)

Dans le portail `/portal`, les administrateurs SaaS peuvent gérer les trois documents légaux depuis **Administration commerciale > Documents légaux** : modifier les titres et contenus, régler la visibilité des liens publics et après connexion, puis enregistrer. Chaque document dispose d'un bouton **Aperçu** qui affiche les valeurs actuellement saisies, même avant enregistrement, sans les publier. Les titres de section (`# `) et les listes (`- `) utilisent le même rendu que les pages publiques ; le HTML reste du texte, sans être exécuté.

**Important :** l'administration de la plateforme (organisations, abonnements, factures, assistance, tarifs, promotions, partenaires, FAQ, formations, base de données, équipe) est désormais **uniquement** dans le portail employé (`/portal`), réservée au rôle `PLATFORM_ADMIN`. L'ancienne section `/app#platform` n'est plus proposée et les routes `/api/platform` répondent `410`. Créez les comptes du portail avec `scripts/create-portal-staff.js`. Procédure historique (comptes `SUPER_ADMIN`, sans effet sur l'administration) :

1. Démarrez MySQL et l’application, puis trouvez l’identifiant d’un établissement actif. Après le seed, vous pouvez exécuter :
   ```sql
   SELECT id, name, slug FROM organizations WHERE slug='demo-health' AND status='active';
   ```
   Vous pouvez choisir un autre établissement actif si ce slug n’existe pas.
2. Ouvrez une fenêtre PowerShell **dans le dossier du projet** (celui qui contient `package.json`). Remplacez `ID_TROUVE` par le nombre obtenu à l’étape 1, puis remplacez le nom et l’adresse par ceux du membre de votre équipe :
   ```powershell
   $env:PLATFORM_ADMIN_ORGANIZATION_ID = "ID_TROUVE"
   $env:PLATFORM_ADMIN_NAME = "Nom de l'administrateur"
   $env:PLATFORM_ADMIN_EMAIL = "superadmin@votre-domaine.com"
   $securePassword = Read-Host "Saisissez un mot de passe temporaire (12 caractères minimum)" -AsSecureString
   $passwordPointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($securePassword)
   try {
       $env:PLATFORM_ADMIN_PASSWORD = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($passwordPointer)
       npm run platform:admin
   } finally {
       [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($passwordPointer)
       Remove-Item Env:PLATFORM_ADMIN_PASSWORD -ErrorAction SilentlyContinue
   }
   ```
   PowerShell vous demandera le mot de passe sans l’afficher. Utilisez un mot de passe temporaire unique, de 12 à 128 caractères. Laissez cette fenêtre ouverte jusqu’au message `Compte SUPER_ADMIN créé.`; le script lit la configuration `.env`, se connecte à MySQL et crée le compte sur l’organisation dont vous avez fourni l’ID. Les trois premières variables ne sont valables que dans cette fenêtre. Ne mettez pas de vrais identifiants dans le dépôt ou un fichier versionné. Le script exige un établissement actif et refuse une adresse déjà utilisée.
3. Ouvrez `http://localhost:3000/connexion` et connectez-vous avec l’adresse et le mot de passe définis à l’étape 2.
4. Une fois connecté, ouvrez **Administration SaaS** dans le menu latéral, ou allez directement sur `http://localhost:3000/app#platform`. La section **Vue générale** liste les organisations et leur abonnement (forfait, état et période); utilisez les contrôles de chaque organisation pour modifier son statut ou son abonnement. Les autres onglets servent à configurer les tarifs, suivre les factures et gérer l’assistance, la FAQ, les formations et l’équipe plateforme.

Si le menu **Administration SaaS** n’apparaît pas, le compte connecté n’a pas le rôle `SUPER_ADMIN`; un compte `OWNER` ou `ADMIN` ne peut voir que la gestion de sa propre entreprise. Après la création du premier Super Admin, fermez la fenêtre PowerShell ou effacez les variables avec `Remove-Item Env:PLATFORM_ADMIN_ORGANIZATION_ID, Env:PLATFORM_ADMIN_NAME, Env:PLATFORM_ADMIN_EMAIL, Env:PLATFORM_ADMIN_PASSWORD`. Pour ajouter d’autres membres de l’équipe, ouvrez **Administration SaaS > Équipe SaaS**.

## Portail de l’équipe, partenaires et marketing

L’espace employé est accessible sur `/portal` et ses fonctions commerciales sont réservées au rôle `PLATFORM_ADMIN`. L’onglet **Administration commerciale** permet de modifier et créer des forfaits personnalisables avec leurs fonctionnalités, tarifs par période et quotas; les promotions peuvent cibler un forfait précis ou s’appliquer à tous, être limitées par dates ou réservées aux nouveaux clients. Le portail permet aussi de gérer les partenaires et leurs codes de parrainage, configurer taux, catégories et fréquence de versement, et générer un rapport marketing exportable en CSV.

Les liens partenaires utilisent `/inscription?ref=CODE`. Une organisation est rattachée au partenaire lors de son inscription; les commissions sont calculées sur chaque facture payée selon le taux partenaire ou le taux par défaut. Les paiements de commissions sont saisis manuellement avec une référence, et le versement ne marque payées que les commissions dues dans la période configurée. Les rapports marketing sont disponibles à partir de la date d’inscription ou de paiement enregistrée dans le système.

L’onglet **Base de données** est réservé à `PLATFORM_ADMIN`. Il affiche l’état, l’aperçu et le journal des migrations versionnées livrées avec l’application; il ne permet pas de saisir ou d’exécuter du SQL libre. Avant chaque migration, le serveur crée une sauvegarde SQL complète avec `mysqldump`; la migration est bloquée si la sauvegarde échoue. Installez les outils client MySQL sur le serveur et rendez `mysqldump` accessible dans son `PATH`, ou définissez `MYSQLDUMP_PATH`. Les sauvegardes sont stockées dans `storage/database-backups` et peuvent être téléchargées depuis l’onglet. Les DDL MySQL peuvent produire une application partielle en cas d’erreur et ne garantissent pas de retour arrière automatique; vérifiez l’aperçu et conservez les sauvegardes hors du serveur. Pour ajouter une évolution, déployez d’abord le code et sa migration versionnée, puis demandez son application dans l’interface; les fonctionnalités nécessitant du nouveau code ne sont disponibles qu’après le déploiement correspondant.

## Architecture
Express REST API + MySQL 8 partagé. Chaque utilisateur est rattaché à une organisation. Le tenant est dérivé du compte authentifié, jamais du navigateur. Les requêtes métier filtrent par `organization_id`. JWT, bcrypt, RBAC simple, Helmet, rate limiting et journal d'audit.

## Modules présents dans ce prototype
Le catalogue affiche le coût moyen d'achat HT lorsqu'il est connu, le prix de vente HT, leur écart unitaire et la marge théorique sur le stock disponible. Il s'agit d'estimations au prix actuel, sans taxe ni frais : elles ne constituent pas le bénéfice réalisé. Le coût moyen est recalculé lors des réceptions de commande. Pour un stock existant dont le coût est inconnu, renseignez manuellement un coût d'ouverture vérifié ; les réceptions ne devinent pas sa valeur. Une entrée manuelle, une réintégration de vente ou une correction modifiant le stock rend le coût inconnu jusqu'à sa vérification. Les données antérieures ne sont pas reconstituées.

Sur une base existante, appliquez depuis le portail employé la migration `2026110601_product_purchase_cost` après sauvegarde, avant de démarrer la nouvelle version. Pour une nouvelle base, `npm run db:init` prépare cette colonne. Ces estimations ne remplacent pas un module de comptabilité ni des états financiers validés.

La migration `2026110603_sale_unit_purchase_cost` est également requise avant d'utiliser les ventes avec cette version : prévisualisez-la et appliquez-la depuis le portail employé après sauvegarde. Chaque nouvelle ligne de vente conserve transactionnellement le coût moyen connu au moment de la sortie de stock ; une valeur inconnue reste nulle, et les ventes antérieures ne sont pas reconstituées. Cette donnée prépare l'inventaire permanent mais ne génère pas encore d'écriture ni de coût des ventes comptable. Les retours et annulations continuent de rendre le coût moyen du stock inconnu lorsqu'ils réintègrent des produits.

Le menu distinct **Comptabilité · à venir**, visible aux propriétaires et administrateurs dont le forfait comprend le module Rapports, présente six sous-modules : état des résultats, bilan, journal comptable, grand livre, flux de trésorerie et taxes. Les six interfaces sont expérimentales et désactivées par défaut ; les déclarations fiscales, les périodes clôturées et les états officiels restent indisponibles.

Le socle comptable expérimental permet de créer un dossier et son plan de comptes, d'enregistrer des brouillons, de valider des écritures équilibrées et de consulter des rapports sur les écritures validées. Il est désactivé par défaut ; `ACCOUNTING_EXPERIMENTAL_ENABLED=true` ne doit être utilisé que dans un environnement de test isolé. Il nécessite la migration `2026110602_accounting_book`, à prévisualiser et appliquer après sauvegarde depuis le portail employé. Il est réservé aux propriétaires et administrateurs dont le forfait comprend Rapports. On peut ajouter des comptes au plan depuis l'état des résultats ; les comptes existants ne sont ni modifiables ni supprimables, et l'ajout est audité en transaction. Une écriture validée ne peut pas être modifiée ; une correction doit faire l'objet d'une nouvelle écriture.

Les nouvelles créations, modifications de brouillons et validations d'écritures conservent leurs détails dans le journal d'audit, dans la même transaction ; pour une modification, les valeurs avant et après sont enregistrées. Les événements antérieurs à cette amélioration ne sont pas reconstitués. Cette traçabilité ne constitue ni une clôture ni une validation professionnelle des rapports.

Un rôle **Expert-comptable** est préparé pour un compte d'un seul établissement, créé ou désactivé par son propriétaire ou administrateur dans Utilisateurs & rôles. La migration `2026110604_accountant_role` doit être prévisualisée puis appliquée après sauvegarde depuis le portail employé avant d'attribuer ce rôle sur une base existante. Le compte utilise le mot de passe initial transmis par l'administrateur : aucune invitation par e-mail n'est envoyée. Il est soumis au quota d'utilisateurs, à l'accès Rapports et au drapeau expérimental, et ses requêtes sont limitées à la comptabilité et à la gestion de son propre mot de passe. Il peut gérer le plan, les brouillons et valider des écritures, sans modifier les écritures déjà validées. Utilisez une adresse e-mail unique, car la connexion actuelle n'offre pas de choix d'établissement.

Ce rôle n'établit pas la qualification professionnelle de son titulaire. La migration `2026110605_accounting_review` doit également être prévisualisée puis appliquée après sauvegarde, y compris pour une nouvelle base. Dans **Comptabilité → Révision comptable**, un propriétaire, administrateur ou expert peut figer un préliminaire sur une période. Il contient le plan, les écritures validées et les six rapports disponibles ; les rapports de trésorerie et de taxes sont indisponibles lorsque leurs comptes ne sont pas configurés. L'expert peut examiner et exporter les rapports puis confirmer la version finale. Si les écritures, le plan ou la devise ont changé, il faut créer et examiner un nouveau préliminaire. Chaque version conserve son empreinte SHA-256 et la validation est auditée ; l'empreinte détecte une altération accidentelle mais n'est pas une signature numérique.

Une version finale est une photographie figée et validée dans l'application, **pas** une certification, une clôture ni un dépôt fiscal. Les écritures ultérieures restent possibles : il faut créer une nouvelle version pour les inclure. Les contrôles de conformité SYSCOHADA, les justificatifs et la clôture restent à développer ; les rapports demeurent expérimentaux et non officiels.

La sauvegarde JSON de l'établissement n'inclut ni dossier, ni écritures comptables, ni versions de révision et ne permet pas de les restaurer. Une sauvegarde complète de la base, conservée et testée séparément, reste nécessaire ; la sauvegarde créée avant une migration ne constitue pas à elle seule une stratégie de sauvegardes régulières.

### Séparer la vente de l'encaissement

Pour chaque paiement en espèces, le champ **Espèces reçues** est obligatoire et doit couvrir le montant encaissé, aussi bien à la saisie d'une vente qu'à l'encaissement d'une facture. Aucun montant reçu n'est déduit automatiquement. Ce champ n'est pas requis pour les autres modes de paiement.

Sur une base existante, prévisualisez puis appliquez la migration `2026110701_separate_sale_payment` depuis le portail employé après sauvegarde, avant de démarrer la nouvelle version. Sur une nouvelle base, l'initialisation prépare les colonnes. Le propriétaire ou l'administrateur choisit le mode dans **Paramètres → Circuit de vente**. Le mode **Un temps** est sélectionné par défaut : le pharmacien ou le caissier peut saisir et encaisser avec une caisse ouverte et les modules Ventes et Caisse inclus dans le forfait.

En mode **Deux temps**, le pharmacien enregistre la vente sans paiement, même si la caisse est fermée, puis dirige le client vers la caisse ; le stock est déduit immédiatement et le statut est **À payer**. Le caissier ne peut pas saisir de nouvelle vente et le pharmacien ne peut pas accéder à la caisse ni enregistrer de paiement ou remboursement. Le caissier, avec accès aux modules Ventes et Caisse, ouvre la caisse et choisit la facture dans le module séparé **Recettes & caisse → Ventes à encaisser**. Les propriétaires et administrateurs gardent les deux accès. Les paiements partiels sont permis : le statut devient **Partiellement payée**, puis **Payée** lorsque le solde est réglé. Le vendeur ne peut jamais encaisser sa propre vente préparée, y compris s'il est administrateur. Les paiements et mouvements de caisse restent traçables ; l'annulation d'une vente non payée réintègre le stock.

Le choix est figé sur chaque nouvelle vente : modifier le réglage ne change pas les ventes déjà créées. Une vente préparée reste à encaisser par un caissier ou administrateur distinct du vendeur, même après le passage au mode Un temps. Les droits des rôles suivent le mode actuel et sont vérifiés côté serveur. Les ventes antérieures à la migration conservent le fonctionnement initial. La liste de caisse est paginée dans l'ordre de création ; la recherche porte sur la page affichée. Le mode ne réserve pas un stock supplémentaire à l'encaissement et ne constitue pas une clôture comptable.

Le menu, les groupes vides et les accès rapides masquent les modules non autorisés selon le rôle, le forfait et le circuit de vente. Les liens directs sont également contrôlés. Les paramètres de l'établissement restent réservés aux propriétaires et administrateurs ; les autres utilisateurs disposent d'un accès séparé à leur mot de passe. La recherche générale ne présente pas de dossiers patients ni d'assurances aux rôles sans accès à ces modules (les listes minimales nécessaires au point de vente restent disponibles dans la vente).

Les droits de module sont indépendants du forfait : un forfait complet n'accorde pas tous les modules à chaque utilisateur. Le caissier est limité aux ventes, factures et caisse ; le pharmacien aux ventes, patients et assurances (et à la caisse en mode Un temps) ; le gestionnaire de stock aux stocks et approvisionnements ; le rôle Consultation seule aux stocks, approvisionnements et rapports en lecture seule. Les propriétaires et administrateurs gardent leurs accès de gestion et l'expert-comptable reste limité à la comptabilité. L'assistance et le changement de mot de passe restent accessibles aux utilisateurs opérationnels. Les API des modules appliquent les mêmes restrictions ; les listes dédiées du point de vente ne donnent accès ni aux coûts d'achat, ni aux coordonnées et antécédents médicaux.

### Fusion des rôles, documents de vente et notifications

Appliquez la migration additive `2026110702_merge_pharmacist_storekeeper` après sauvegarde **avant de démarrer cette version** sur une base existante. Elle ajoute uniquement un réglage désactivé par défaut et ne remplace aucun rôle utilisateur. Ne lancez pas `db:init` ou `db:seed` sur la production.

Dans **Paramètres → Fusion des rôles**, le propriétaire ou administrateur peut réunir les droits des pharmaciens et gestionnaires de stock. Tous ces comptes, anciens ou nouveaux, affichent alors **Pharmacien / Gestionnaire de stock** et disposent des ventes, patients, stocks et approvisionnements autorisés par le forfait. Désactiver la fusion rétablit leurs droits d'origine. Le serveur relit le réglage à chaque requête ; rechargez la page pour actualiser le menu des sessions ouvertes. En deux temps, les deux rôles fusionnés saisissent sans encaisser ; ils ne peuvent pas régler une facture préparée, même après retour au mode un temps. La fusion ne donne aucun droit administrateur ou comptable.

Les factures/reçus de vente affichent le nom de l'entreprise, ses coordonnées et son logo lorsqu'il est configuré dans **Paramètres → Généraux & identité**. Un code-barres **Code 128** contient le numéro de facture. Dans **Recettes & caisse**, le champ de scan retrouve cette facture dans tout l'établissement, indépendamment de la pagination, et ouvre le paiement seulement si la caisse est ouverte et l'utilisateur autorisé. Le bouton **Scanner la vente** ouvre une fenêtre qui accepte au choix la caméra (HTTPS et autorisation du navigateur requises, caméra arrière privilégiée) ou un lecteur de code-barres USB/Bluetooth configuré en mode clavier avec validation par Entrée. Si la caméra est refusée ou absente, le lecteur reste utilisable; la caméra est arrêtée dès qu'une facture est lue ou que la fenêtre est fermée.

Chaque vente crée, dans la même transaction, une notification privée aux utilisateurs actifs de l'établissement autorisés à accéder à la caisse selon le circuit et le forfait, y compris pour une vente déjà payée en un temps. Les notifications sont vérifiées toutes les dix secondes tant que la session est ouverte. Chaque nouvelle notification déclenche un bip après une première interaction utilisateur. Le panneau des notifications permet d'activer ou désactiver le son ; les anciens messages ne sont pas rejoués au chargement. Les navigateurs peuvent suspendre les onglets en arrière-plan : il ne s'agit pas d'une notification push lorsque l'application est fermée.

### Mise à jour SQL d'une base existante

Le fichier [upgrade-preserve-data.sql](database/upgrade-preserve-data.sql) applique uniquement les huit migrations versionnées livrées, de `2026110501` à `2026110702`, sur MySQL 8. Il ajoute les colonnes, contraintes et tables comptables manquantes et étend le rôle utilisateur sans supprimer de rôle existant. Il ne réinitialise aucune table, ne modifie aucune valeur métier existante et n'insère aucune donnée de démonstration. Les nouvelles colonnes de coût restent inconnues (`NULL`), la fusion des rôles et la séparation vente/caisse sont désactivées par défaut pour les lignes existantes. Les colonnes déjà présentes et leurs valeurs ne sont pas remplacées.

1. Arrêtez les ventes et toutes les autres écritures de l'application. Conservez une sauvegarde SQL complète hors du serveur et vérifiez qu'elle peut être restaurée sur une base isolée. Par exemple, avec les outils MySQL : `mysqldump --host=SERVEUR --user=UTILISATEUR --password --single-transaction --routines --triggers --events --hex-blob --set-gtid-purged=OFF --no-tablespaces --result-file=sauvegarde-avant.sql NOM_BASE`. Le mot de passe est demandé, ne l'inscrivez pas dans la commande.
2. Dans une copie du fichier SQL, remplacez `SET @redams_expected_database = NULL;` par `SET @redams_expected_database = 'NOM_BASE';`, puis mettez `@redams_backup_confirmed` à `1` seulement après vérification de la sauvegarde.
3. Connectez-vous à la base existante dans MySQL Workbench ou dans le client `mysql --host=SERVEUR --user=UTILISATEUR --password NOM_BASE`. Avec le client MySQL, exécutez `SOURCE C:\chemin\upgrade-preserve-data.sql;`. L'outil doit prendre en charge `DELIMITER`, les procédures et les instructions préparées. Le compte doit pouvoir lire les métadonnées, créer/supprimer cette procédure de migration, créer des tables et modifier les tables existantes.
4. Vérifiez le résultat final et comparez les utilisateurs, stocks, factures, paiements et paramètres à la sauvegarde avant de reprendre les écritures. Conservez la sauvegarde après l'intervention.

Les contrôles de compatibilité sont effectués avant les modifications des tables métier. Une incompatibilité, une référence orpheline ou une migration concurrente bloque l'opération au lieu de corriger automatiquement des données. Ce fichier est réexécutable après inspection et résolution de l'erreur, mais les DDL MySQL ne garantissent pas de retour arrière automatique : un problème de droits, de disque ou une panne en cours d'application peut laisser un schéma partiellement mis à jour. Ne poursuivez pas aveuglément après une erreur. Le script utilise uniquement la procédure réservée `redams_upgrade_preserve_data_2026110701` comme outil temporaire ; il ne faut pas y placer une routine personnalisée.

Le journal des migrations du portail n'est pas modifié ni falsifié par ce fichier autonome. Les migrations non journalisées peuvent donc apparaître en attente avec un aperçu vide après exécution ; le portail peut les vérifier et les journaliser avec sa propre sauvegarde. Ce script n'est pas un outil de mise à niveau d'une base ancienne arbitraire : si des tables préalables manquent, faites examiner son schéma, sans lancer `db:init` ni `db:seed` sur la production.

Dans **Administration commerciale → Tarifs et promotions → Forfaits**, la comptabilité est indiquée sous « Rapports & analyses » : elle n'a pas de tarif indépendant. Pour un forfait personnalisé, sa sélection et son tarif sont ceux de Rapports & analyses ; pour un forfait fixe, ils dépendent du contenu du forfait. Ce rattachement ne garantit pas que le socle expérimental soit activé.

Si une initialisation antérieure s'est arrêtée sur une erreur de syntaxe près de `lines JSON`, elle peut avoir créé une partie des tables avant l'échec : MySQL n'annule pas ces créations. Ne supprimez pas les tables pour recommencer. Vérifiez l'état de la base et disposez d'une sauvegarde avant de reprendre ; sur une base existante, utilisez l'aperçu des migrations du portail employé plutôt que de relancer aveuglément l'initialisation. La correction conserve le nom de colonne et la signature de la migration comptable.

Des interfaces expérimentales permettent de calculer l'état des résultats par période et le bilan à une date donnée, de consulter le journal et le grand livre des écritures validées par période, et de créer le plan initial, saisir et corriger des brouillons puis les valider. Le grand livre détaille les mouvements et les soldes par compte, en débit moins crédit ; son solde initial précède le premier jour sélectionné. Les écritures d'ouverture datées de ce premier jour figurent parmi les mouvements. Le journal exclut les brouillons et affiche chaque ligne ainsi que les totaux de débit et crédit. Le bilan présente les soldes nets classés selon le type attribué à chaque compte et le résultat cumulé non clôturé ; il ne constitue pas une présentation réglementaire SYSCOHADA. La configuration et l'évolution du plan SYSCOHADA, les justificatifs, la clôture et les propositions issues des ventes et achats restent à réaliser. Le moteur ne vérifie pas l'exhaustivité des écritures ni la conformité du plan : ses résultats ne constituent pas des états financiers validés. Ne pas utiliser ce socle en production comptable.

Après calcul, chacun des six rapports peut être exporté en CSV UTF-8 séparé par des points-virgules pour examen manuel par l'expert-comptable. L'export reprend la période ou la date, la devise, les avertissements et les détails du rapport, ainsi que l'éventuel filtre du grand livre. Dates, identifiants, codes et montants sont préfixés d'une apostrophe pour préserver leur représentation textuelle dans un tableur ; retirer ce préfixe lors d'un traitement automatisé. Importer ces colonnes comme texte pour conserver les montants exacts et les zéros initiaux. Ces fichiers confidentiels ne sont pas des sauvegardes ni des états officiels : ils ne contiennent que les écritures comptables validées, pas les brouillons ni les opérations absentes ; même les ventes et achats enregistrés dans le portail ne sont pas automatiquement repris en comptabilité. L'expert doit vérifier et compléter manuellement le périmètre et les justificatifs.

Le rapport expérimental de flux de trésorerie nécessite au moins un compte marqué trésorerie. Il présente, sur les seules écritures validées, les entrées, sorties et flux nets par catégorie choisie manuellement, ainsi que les mouvements associés. La trésorerie initiale inclut les écritures d'ouverture du premier jour sélectionné. Les virements internes ne sont pas éliminés : une écriture comportant à la fois un débit et un crédit de trésorerie est signalée comme virement interne possible, sans certitude. Les flux bruts et les catégories peuvent donc être faussés ; ce rapport ne remplace pas un tableau réglementaire.

Le rapport expérimental de taxes présente les mouvements des comptes manuellement classés taxe collectée ou déductible, hors brouillons et écritures d'ouverture. Par compte, il affiche débit, crédit et variation nette de la période (crédit moins débit pour les comptes classés collectés ; débit moins crédit pour les comptes classés déductibles). Les règlements, transferts et corrections ne sont pas distingués ; ces variations ne représentent donc pas nécessairement les taxes de la période. Une catégorie sans compte est indiquée comme indisponible. Les taux, bases imposables, justificatifs et règles fiscales ne sont pas vérifiés : aucun montant à payer ni déclaration fiscale ne peut être déduit de ce rapport.

Connexion, dashboard, catalogue produits (création, modification, archivage, ordonnance obligatoire et seuils d’achat à vérifier), mouvements entrée/sortie/ajustement, alertes, fournisseurs et commandes d’approvisionnement, registre patient, antécédents datés avec statut, notes et alertes de libellés correspondants à vérifier, organismes assureurs et couvertures patients présentés dans des onglets dédiés, point de vente avec reçus HT/taxe configurable, paiements fractionnés et contrôle de prescription, factures avec paiements, retours/remboursements et traçabilité du stock, caisse avec sessions d’ouverture/clôture, rapprochement des espèces, recettes diverses et dépenses, tables recherchables, filtrables, triables et paginées, recherche générale par modules, paramètres tenant regroupés en onglets (profil entreprise, branding, sauvegarde/fusion, mots de passe et sessions, format d’étiquette et diagnostic d’index), notifications générales ou privées (historique paginé, envoi réservé aux administrateurs), logo tenant, génération QR, consultation abonnement et aperçu des métriques plateforme (route SUPER_ADMIN). Les opérations financières et les mouvements de stock sont enregistrés avec l’utilisateur et l’organisation ; les factures, retours et sessions clôturées restent traçables.

Le module Administration permet aux propriétaires et administrateurs de gérer les comptes de leur établissement : création, modification, attribution des rôles disponibles, réinitialisation manuelle du mot de passe, activation/désactivation et respect du quota d’utilisateurs du forfait. Seul un propriétaire peut gérer les rôles privilégiés; le dernier propriétaire actif ne peut pas être désactivé ou rétrogradé. Les comptes sont conservés pour préserver la traçabilité. Le journal d’activité est consultable en lecture seule, filtrable par recherche, action, type d’objet et dates, avec pagination. Les opérations d’administration sont elles-mêmes journalisées.

Le module « Rapports & analyses » propose des vues de synthèse, ventes, stocks, tendances internes et prévisions, avec des graphiques interactifs (survol des points), des comparaisons de périodes, des tableaux filtrables, un export CSV et des plages de 7, 30, 90 ou 365 jours. Les ventes globales sont calculées TTC après remboursements; les comparaisons par produit et catégorie sont estimées HT à partir des prix unitaires. Les alertes de couverture et les projections de revenus/stock reposent sur les ventes historiques moyennes; elles sont indicatives, ne tiennent pas compte de la saisonnalité et ne déclenchent pas de réapprovisionnement. Les analyses dites de marché décrivent uniquement les ventes et catégories de l’établissement : aucune donnée de marché externe ni concurrence n’est intégrée.

Les paramètres permettent de télécharger une sauvegarde JSON tenant-scoped et de fusionner une sauvegarde du même établissement : seuls les enregistrements manquants sont ajoutés, les conflits annulent la transaction. L’export exclut les comptes utilisateurs et abonnements, mais inclut les logos enregistrés en base depuis la migration `2026111201_database_logo_storage`. Les logos historiques enregistrés uniquement dans `public/uploads/logos` ne sont pas inclus. Les ordonnances font partie de l’export et sont des données médicales sensibles; protégez les fichiers. Le changement de mot de passe vérifie l’ancien mot de passe et révoque les sessions existantes; un administrateur peut également réinitialiser le mot de passe d’un membre. Le diagnostic vérifie les index présents dans le schéma MySQL partagé; l’actualisation des statistiques concerne les tables partagées par tous les établissements.

Le module Assistance comprend une FAQ et des formations publiées par l’équipe REDAMS, des demandes techniques et un chat direct avec jeton de suivi. Les échanges du chat sont actualisés périodiquement; si aucun agent n’est disponible, la demande reste en attente. Seuls les comptes `SUPER_ADMIN` actifs peuvent utiliser l’administration plateforme. La navigation offre les sections Vue générale (établissements, abonnements, chats), Tarifs & promotions (forfaits, quotas et codes de réduction), Facturation (création de brouillons d’abonnement, émission, suivi et enregistrement manuel des paiements), Assistance (demandes techniques et chats), FAQ, Formations et Équipe SaaS. Les opérations sensibles sont réservées aux routes `/api/platform` protégées par le rôle `SUPER_ADMIN`, et journalisées. La gestion d’un compte d’équipe se fait dans Équipe SaaS; la création exige un mot de passe temporaire d’au moins 12 caractères, transmis à son destinataire par un canal sécurisé. Les promotions actives sont proposées sur le portail et à la souscription; l’équipe SaaS peut aussi les appliquer aux factures. Aucun prélèvement, paiement en ligne, envoi automatique de facture ou de courriel n’est intégré.

Dans le portail plateforme, « Horaires de travail » conserve les horaires planifiés et permet aux employés de pointer le début et la fin de leur journée. L’historique présente les heures pointées, les tickets de support clôturés, leur origine (assignation par un administrateur ou prise en charge volontaire), le délai de traitement et les avis clients, par semaine, 14 derniers jours, mois ou année. Le délai est mesuré entre l’assignation et la clôture; il ne représente pas nécessairement du temps de travail actif. Les heures ne sont disponibles qu’à partir de l’activation du pointage, et les anciens tickets sans dates d’assignation/clôture ne sont pas reconstitués. Le demandeur peut laisser une note de 1 à 5 et un commentaire après la clôture d’un ticket.

Le catalogue permet d’imprimer une étiquette par produit ou de sélectionner les produits en lot, au format code-barres Code 128 ou QR. Les produits sans code reçoivent à la génération un identifiant unique enregistré dans leur champ code-barres; le scanner du point de vente le reconnaît ensuite. La génération QR et l’impression en lot sont disponibles depuis le catalogue; les doublons détectés doivent être corrigés avant impression.

Les fonctions de vente et de caisse sont accessibles aux rôles `OWNER`, `ADMIN`, `PHARMACIST` et `CASHIER`. Les modes de paiement sont saisis manuellement (aucune passerelle bancaire/mobile n’est intégrée) ; le mode assurance exige une couverture patient active. Pour appliquer ce mode, les rôles de vente reçoivent uniquement le nom de l’assureur actif du patient ; les détails des contrats restent réservés aux rôles `OWNER`, `ADMIN` et `PHARMACIST`. Les ventes nécessitent une session de caisse ouverte et l’interface affiche explicitement l’erreur si la caisse est fermée. Le bouton « Scanner un code », à côté de l’ajout manuel d’un produit, ouvre une fenêtre simple qui reste ouverte pour scanner les articles en cascade : elle affiche la quantité totale et le nombre de références du panier, et émet un petit bip à chaque lecture réussie. On peut saisir successivement les codes avec une douchette USB/Bluetooth ou activer la caméra du PC, téléphone ou tablette. La lecture caméra ignore les répétitions d’un même code tant qu’il reste dans le champ de vision. Elle utilise ZXing localement dans l’application (sans envoi de l’image à un service externe), prend en charge les codes-barres et QR dans les navigateurs courants disposant de l’accès caméra; HTTPS ou localhost et l’autorisation caméra sont requis. Les annulations ne sont possibles qu’avant encaissement ; après paiement, utilisez le retour/remboursement qui calcule le montant depuis les lignes originales et peut réintégrer les quantités au stock. Si un produit requiert une ordonnance, sa présentation doit être confirmée et une image doit être jointe à la vente ; elle est conservée avec la facture (JPEG, PNG ou WebP, 500 Ko maximum) et sa consultation est limitée aux rôles `OWNER`, `ADMIN` et `PHARMACIST`. Les seuils de quantité et d’intervalle par produit produisent des alertes indicatives, jamais une décision médicale ni un blocage automatique. L’accès aux antécédents reste limité aux rôles `OWNER`, `ADMIN` et `PHARMACIST`. Les correspondances de libellés normalisés sont seulement des alertes de dossiers à faire vérifier par un professionnel : elles ne diagnostiquent ni ne confirment une récidive ou une récurrence. Les formulaires d’antécédents ne remplacent pas un dossier médical ni un système clinique validé.

Après mise à jour, exécute `npm run db:init` pour créer les tables requises et ajouter de façon idempotente les nouveaux paramètres aux tables existantes, puis relance le serveur.

Les paramètres d’identité permettent de renseigner séparément le nom, l’adresse, le téléphone, le slogan et le courriel de l’entreprise, puis de charger son logo (PNG, JPEG, GIF ou WebP, 2 Mo maximum). Les logos sont enregistrés dans la base de données afin de survivre aux déploiements GitHub et sont inclus dans les sauvegardes de base de données. Après le déploiement de la migration `2026111201_database_logo_storage`, les logos qui avaient été supprimés du dossier `public/uploads/logos` doivent être téléversés de nouveau.

Dans le reçu, choisissez Portrait ou Paysage avant de cliquer sur Imprimer. Le format A4 utilise une marge haute nulle, des marges latérales de 0,5 cm et une marge basse de 1,5 cm. Les réglages de l’imprimante peuvent imposer une zone non imprimable.

Le portail public permet de choisir un forfait, une période de facturation et une promotion active, puis de créer immédiatement un espace avec un essai gratuit de 7 jours incluant toutes les fonctionnalités. Starter inclut les stocks, l’approvisionnement, les ventes et la caisse pour 3 utilisateurs; ses prix par défaut sont de 15 000 XAF/mois, 150 000 XAF/an ou 280 000 XAF/2 ans, puis 5 000 XAF par utilisateur ajouté. Ultimate inclut toutes les fonctionnalités pour 5 utilisateurs et coûte 25 000 XAF/mois, 350 000 XAF/an ou 600 000 XAF/2 ans, puis 5 000 XAF par utilisateur ajouté. Customized permet de choisir les fonctionnalités et le nombre d’utilisateurs : chaque fonctionnalité coûte 10 000 XAF/mois, 120 000 XAF/an ou 240 000 XAF/2 ans, à l’exception du module Stock à 12 000 XAF/mois, 120 000 XAF/an ou 240 000 XAF/2 ans. Les offres et réductions se gèrent dans Administration SaaS > Tarifs & promotions; les promotions actives sont proposées lors de l’inscription. Les fonctionnalités non incluses sont bloquées côté API. Les entreprises Starter gardent la gestion de leurs utilisateurs; le journal d’activité est réservé aux offres qui comprennent Administration. Pendant l’essai, toutes les fonctionnalités sont accessibles quel que soit le forfait choisi. À l’échéance de l’essai, seules les fonctionnalités du forfait choisi restent actives; les autres sont désactivées dans l’interface et bloquées côté API. La facturation reste manuelle et aucun paiement n’est prélevé automatiquement.

## Limites
La récupération de mot de passe par SMTP, les paiements récurrents et l’intégration à des prestataires de paiement restent des points d’extension; la gestion d’abonnement dans l’administration SaaS est manuelle. Les modules patients et assurance ne constituent pas un dossier clinique ni un traitement automatisé des récidives. Le prototype n'est pas prêt à héberger de vraies données médicales ni à traiter de vrais paiements. Un audit de sécurité et de conformité est requis avant production.
